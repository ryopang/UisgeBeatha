# Uisge Beatha: end-to-end audit

November 2026 · Reviewer stance: senior iOS engineer plus UI/UX review · Scope: every Swift file, tests, project settings, data sources, docs

## Verdict

The approach is right. Keep it.

A native SwiftUI + SwiftData app with zero dependencies, no backend, and on-device intelligence is the correct shape for a personal-collection app with fewer than a few hundred records per user. Nothing about it needs a server, and the owner's constraints (no recurring cost, privacy, offline use) all point the same way. The v1 code is disciplined: protocol-first services, a data-driven region catalog, a CloudKit-safe schema, one strings file, and a label-OCR pipeline backed by a measured accuracy corpus.

What it is not yet is an App Store product that is great on both an iPhone and an iPhone Duo. The gaps are specific:

1. **No adaptive layout.** Every screen is a single-column stack. On the Duo's 7.6" inner display (regular width, like a small iPad) that wastes most of the screen.
2. **Heavy work on the main actor.** The project defaults to `MainActor` isolation, so photo downsampling (`ImageStore.save`) and live label parsing (on every camera frame) run on the main thread.
3. **No schema versioning.** CloudKit sync and photo sync need a `VersionedSchema` and a migration plan before any v2 model change ships.
4. **Third-party image hotlinking.** Stock photos are stored as remote URLs and loaded live. That breaks offline, rots when hosts change, leaks the user's IP to arbitrary retailer sites, and can't sync.
5. **Accessibility gaps** in contrast, touch targets, and layouts at large Dynamic Type sizes, now partly fixed.

The rest of this report covers what I fixed in this pass and what's left, ranked by priority.

## Open findings, ranked

P0 blocks App Store release or risks data loss. P1 should land in v2.0. P2 is v2.x. P3 is nice to have.

### Architecture and persistence

- **P0. Add `VersionedSchema` + `SchemaMigrationPlan` before any model change.** Today `ModelContainer(for: Bottle.self, TastingNote.self)` has no version. The first v2 change (photo sync, see below) without one risks a store that won't open. Wrap the current models as `SchemaV1` with no shape change, ship that, then add `SchemaV2`.
- **P0. Replace `fatalError` on container creation** with a recovery screen: offer an export of whatever can be read, then a reset. A crash loop on launch is the worst failure mode for a collection app.
- **P1. Photos must become syncable.** `LocalImageStore` writes files to Application Support, and CloudKit mirroring syncs model attributes only. Plan: a `BottlePhoto` model (`@Attribute(.externalStorage) var imageData`, `thumbnailData`, relationship to `Bottle`) behind the existing `ImageStore` protocol, plus a one-time migrator. The protocol was designed for exactly this.
- **P1. Stop hotlinking stock photos.** Download the chosen stock image once (downsampled through the same ImageStore path), store it as the bottle's "stock" photo, and keep the source URL only for attribution. This fixes offline use, link rot, IP leakage to arbitrary retailer hosts, and sync in one move.
- **P1. Pull flow logic out of views.** `ScanView` (400+ lines) owns duplicate check, lookup, policy gate and sheet routing. `BottleFormView` (430+ lines) owns validation, label parsing and photo persistence. Move each into a small `@Observable` model (`ScanFlow`, `BottleDraft`). That makes them unit-testable and lets the Duo layout show the same flow in a side panel instead of a sheet.
- **P2. CloudKit duplicate merging.** Two devices adding the same barcode offline produces two records. Dedupe on remote-change notifications by barcode, keeping the older `dateAdded` and merging notes.
- **P2. `Decimal` price under CloudKit.** Verify that `Decimal` mirrors cleanly. If it doesn't, migrate to `priceMinorUnits: Int?`, which is the safer money type anyway.

### Concurrency and performance

- **P1. `ImageStore.save` runs on the main actor.** Under `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, two ImageIO downsample-and-encode passes of a 12 MP capture run on the main thread when a photo is applied (a visible hitch). Make `LocalImageStore` a `nonisolated` type with `async` methods (or an actor) and `await` it.
- **P1. Live label parsing runs on every camera frame, on main.** `liveLabelResult` re-runs `LabelParser.parse` (windowed fuzzy matching against 126 distilleries) on each `DataScannerViewController` text update. Throttle it to about 4 Hz and move it to a `nonisolated` parser. `DistilleryStore` and `ExpressionStore` are already value types, so the change is annotations plus a `Task`.
- **P2. Synchronous thumbnail reads in list rows.** `BottleThumbnailView` calls `UIImage(contentsOfFile:)` during `body`. Add an in-memory thumbnail cache (`NSCache`) and load it asynchronously. This matters at hundreds of bottles, not dozens.
- **P2. Cold launch.** `DistilleryStore`/`ExpressionStore` load and the custom-words list builds synchronously in `App.init`. That's fine today, but measure it with Instruments against the PRD's under-1-second target once sync and photos land.

### Security and privacy

- No secrets, keys, accounts or servers. Attack surface is small.
- **P1.** Third-party lookups send barcodes and search terms (and the device IP) to Open Food Facts, UPCitemdb and Wikimedia. Say so in the privacy policy. The App Privacy label can still be "Data Not Collected" because the developer receives nothing.
- **P2.** The Settings copy "Nothing is uploaded anywhere" becomes false once CloudKit sync ships. Change it to "Synced privately through your iCloud account."
- **P3.** Exports land in `tmp/` as plaintext. That's acceptable, but delete them after the share sheet completes.

### UI, UX and accessibility

- **P0 for Duo.** Single-column layouts everywhere. See the PRD's adaptive layout spec.
- **P1. No state restoration.** Folding or unfolding the Duo changes size class. Views that branch on size class get rebuilt and lose state, and a rebuilt `DataScannerViewController` restarts the camera. Keep view identity stable across size classes, and persist selection with `@SceneStorage`.
- **P1. Dark-mode prominent buttons.** White text on dark-mode amber `#DE8230` is about 2.9:1. Either use dark text on amber in dark mode or a deeper fill. Decide this as part of the design system, not as a one-off.
- **P1. Hero image** is a fixed 280pt `scaledToFill`. On the inner display's wide detail column that crops bottles badly. Bottles are tall: use `scaledToFit` on a neutral backdrop, or an aspect-aware frame.
- **P2. Tasting wheel** is reference-only with 9pt labels that don't scale with Dynamic Type. Make descriptors tappable (inserting into the focused note field) and provide an accessible list alternative.
- **P2. Map zero-count badges** use `.gray` at 70% opacity. Pick a token that passes 3:1 in both modes.
- **P2. Motion.** Only the duplicate toast animates. Add purposeful, interruptible transitions (sheet-to-detail matched geometry for bottle photos, a status-cycle bounce via `symbolEffect`) and respect Reduce Motion. See the PRD's motion section.
- **P3. Search** covers name and distillery only. Add region, cask and status tokens (`searchable` tokens).

### Docs and tooling

- **`DESIGN.md` is the wrong document for this app.** It describes Apple's *marketing website* (Action Blue `#0066cc`, px type scales, web components) and contradicts the app's actual amber accent and Dynamic Type. It will mislead future AI sessions. Replace it with the iOS design system in PRD §8, or delete it. Left untouched in this pass because it's your file.
- **No CI.** Add an Xcode Cloud workflow (25 compute hours a month are included with the developer program): build plus unit tests on every PR, UI tests nightly.
- **`TARGETED_DEVICE_FAMILY = "1,2"`.** The app is built for iPad too, which the v1 PRD said it wasn't. The adaptive layout makes iPad nearly free, so keep it but test it, or set it to `1` until then. Note that an iPad target needs iPad screenshots for App Store review.

## iPhone Duo readiness

Facts, as published by Apple and in launch coverage (October 2026):

- **Outer display:** 5.4", compact width. Behaves like a small iPhone.
- **Inner display:** 7.6", regular width *and* regular height, like a small iPad. It also supports 50/50 Split View with another app, where the app gets roughly half the width.
- Apple's guidance: branch on size classes, not orientation or device model. Don't use fixed breakpoints tied to either screen.
- How much of the inner display an app gets depends on the SDK it was built with. Building with the **iOS 27 SDK (Xcode 27)** is required for full-screen use.

Current state: the app builds with the iOS 26 SDK and has no size-class handling. On the inner display it would run as a stretched phone layout, or windowed under the older SDK.

What "great on Duo" means is specified in PRD §7.
